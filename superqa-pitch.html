The problem

QA's work lives in four repos and zero shared views

Everything QA produces today is built through terminal agent sessions across four codebases — and reviewed blind:

product-docs

Docs written without the visual

MkDocs content is edited as raw Markdown; you only see the rendered page (and whether the screenshot fits) after a separate build step.

playwright

E2E tests with no map

Dozens of specs, fixtures, and page objects — but no view of what covers which flow, what's flaky, or what a new test should reuse.

web-service-quality

API tests disconnected from E2E

The pytest suite exercises the same endpoints the Playwright specs hit, but nothing records that relationship. Coverage overlaps and gaps are invisible.

platform-lab (core)

Expertise locked in the terminal

All of this runs through CLI agent sessions. Anyone not fluent in that workflow — new QA hires, PMs checking a flow — is locked out.

The cost is concrete: every doc update means a write-build-check loop, every new test risks duplicating coverage nobody can see, and onboarding a QA engineer means teaching four repos plus a terminal workflow before they ship anything.

The idea

A web workbench over the repos we already have

SuperQA is a browser app — think Superset's workspace model, aimed at QA. It doesn't replace the four repos; it mounts them. Each chat session is an agent (Claude or Codex, switchable per task) working in a real checkout, and the right pane renders what the agent just changed.

surface 1

Doc studio

Chat on the left, live MkDocs render on the right. The agent edits Markdown, captures screenshots from real test runs, and you approve what readers will actually see. Output: a normal PR to product-docs.

surface 2

Test studio

Describe a flow; the agent writes the Playwright spec or pytest case, reusing existing fixtures and page objects it can see. Runs execute live in an embedded browser pane with trace and retry info inline.

surface 3

The test tree

An interactive graph of what connects to what: feature → E2E spec → API test → endpoint (from the OpenAPI schema) → doc page. Click a node to see its tests, its last run, and what breaks if it changes.

The test tree is the moat. Chat-plus-preview is table stakes; the graph is what no off-the-shelf tool gives us, because it's built from our own repos: Playwright annotations, pytest markers, and the Giraffe360 OpenAPI schemas we already serve over MCP. It turns "do we cover refunds?" from an archaeology task into a click.

How it works

Thin product, heavy reuse

frontend

Web app

Chat UI, split preview pane, graph view (React + a graph lib). Platform-lab's Tauri shell is a candidate base.

agent layer

Claude Agent SDK / Codex

Each session drives a headless agent in a repo worktree. Model choice is a dropdown, not a commitment.

runners

Existing suites, unchanged

Playwright and pytest run as they do today; SuperQA consumes their JSON reports and traces.

index

Coverage graph

Static parse of specs + markers, joined with the OpenAPI schema index. Rebuilt on merge; rendered as the tree.

Everything merges back through normal PRs — SuperQA is a front end on the existing workflow, not a parallel source of truth. If the product dies, the repos are untouched.

Why now

The hard parts already exist

A year ago this was a platform project. Today the agent loop is a product feature of the Claude Agent SDK and Codex; the embedded-browser pattern is proven by Superset and Claude Code's web UI; and our OpenAPI schemas are already queryable over MCP. What's left to build is the thing that's actually ours: the QA-shaped workspace and the coverage graph.

Plan

Three phases, value at each step

Weeks 1–3

Prototype: Doc studio

Chat + live MkDocs preview over product-docs, Claude only, single user. Success test: one real doc update shipped end-to-end without touching a terminal.

Weeks 4–8

Test studio + first tree

Playwright sessions with embedded browser runs; static coverage index over the E2E and API suites rendered as a clickable tree. Codex added as second model.

Quarter 2

Team rollout

Multi-user sessions, run history, flake tracking on the tree, PM-readable coverage view. Decide then: internal tool forever, or something bigger.

The ask

One engineer-quarter and QA's own dogfooding time. Phase 1 is deliberately small — three weeks to a working doc studio on a real repo. If writing one doc through SuperQA isn't obviously better than the terminal loop, we stop there and have lost three weeks, not a roadmap.
